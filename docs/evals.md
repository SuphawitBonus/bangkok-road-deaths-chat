# ชุดทดสอบ (eval harness)

## ทำไมต้องมี

สัปดาห์ที่ 2 จะต่อโมเดลเข้ามาเขียน SQL คำถามที่ตามมาทันทีคือ **"แล้วรู้ได้ยังไงว่ามันตอบถูก"**
ถ้าวัดด้วยการลองถามเองสิบคำถามแล้วรู้สึกว่าดี จะไม่มีทางรู้เลยว่าการแก้ prompt ครั้งต่อไป
ทำให้ดีขึ้นหรือแย่ลง

ชุดทดสอบนี้คือคำถามพร้อมเฉลยที่ตรวจได้ด้วยเครื่อง ใช้เป็นตัวเลขอ้างอิงว่าเปลี่ยนอะไรแล้ว
คะแนนขยับไปทางไหน

## หลักที่ยึด: เฉลยต้องถูกตรวจก่อน

ปัญหาที่เจอบ่อยในชุดทดสอบคือ **เฉลยเองผิด** ซึ่งทำให้ตัวเลขที่วัดได้ไร้ความหมาย
โมเดลอาจตอบถูกแต่ถูกนับว่าผิด หรือแย่กว่านั้นคือตอบผิดแล้วถูกนับว่าถูก

`npm run evals:verify` จึงรัน `gold_sql` ของทุกข้อกับฐานข้อมูลจริง แล้วเทียบกับเฉลยที่เขียนไว้
**สคริปต์นี้ยังไม่ยุ่งกับ AI เลย** มันตอบคำถามเดียวคือ "เฉลยที่เราเขียน ตรงกับที่ฐานข้อมูลตอบจริงไหม"

สคริปต์ยังส่ง `gold_sql` ทุกข้อผ่านตัวตรวจ SQL ด้วย ถ้าเฉลยของเราเองยังเขียน SQL ที่ตัวตรวจ
ไม่ยอมให้ผ่าน แปลว่าเราตั้งกฎไว้แคบเกินไปจนโมเดลก็จะเขียนให้ผ่านไม่ได้เหมือนกัน
และ `gold_sql` ถูกรันด้วย role `ai_reader` ตัวเดียวกับที่ SQL ของ AI จะถูกรัน ไม่ใช่ role แอดมิน

## รูปแบบไฟล์

`evals/questions.jsonl` — หนึ่งคำถามต่อหนึ่งบรรทัด (JSON Lines)

เลือก JSONL แทน JSON ก้อนเดียวเพราะ: diff ใน git อ่านง่ายเวลาเพิ่มทีละข้อ, ไฟล์พังหนึ่งบรรทัด
ไม่ทำให้ทั้งไฟล์ใช้ไม่ได้และบอกได้ว่าพังบรรทัดไหน, และสัปดาห์ที่ 2 อ่านทีละบรรทัดแบบ stream ได้

| ฟิลด์ | ความหมาย |
| --- | --- |
| `id` | รหัสไม่ซ้ำ เช่น `q001` |
| `split` | `dev` หรือ `test` — ดูหัวข้อ "แบ่งชุด dev / test" |
| `question` | คำถามอย่างที่ผู้ใช้จะพิมพ์จริง |
| `lang` | `th` หรือ `en` |
| `type` | `count` · `ratio` · `trend` · `top-n` · `unanswerable` |
| `gold_sql` | SQL ที่ถูกต้อง เป็น `null` เมื่อเป็นคำถามที่ตอบไม่ได้ |
| `expected` | เฉลย — `{kind:"rows", rows:[...]}` หรือ `{kind:"refusal", ...}` |
| `tolerance` | ความคลาดเคลื่อนที่ยอมรับได้ของตัวเลข ใช้กับทศนิยม |
| `notes` | เหตุผลของเฉลย กับดักของข้อนี้ และสิ่งที่คำตอบที่ดีควรพูดถึง |

### ตัวอย่างข้อที่ตอบได้

```json
{"id":"q001","question":"ปี พ.ศ. 2567 มีผู้เสียชีวิต...กี่ราย","lang":"th","type":"count",
 "gold_sql":"SELECT count(*) AS n FROM deaths WHERE year_be = 2567",
 "expected":{"kind":"rows","rows":[{"n":675}]},"tolerance":0,"notes":"..."}
```

### ตัวอย่างข้อที่ตอบไม่ได้

```json
{"id":"q003","question":"ผู้เสียชีวิตใส่หมวกกันน็อกกี่เปอร์เซ็นต์","type":"unanswerable",
 "gold_sql":null,
 "expected":{"kind":"refusal","must_mention":["หมวกกันน็อก","ไม่มีข้อมูล"],
   "proof_sql":"SELECT count(*) AS n FROM information_schema.columns WHERE ...",
   "proof_rows":[{"n":0}]},"notes":"..."}
```

**`proof_sql` คือหัวใจของข้อประเภทนี้** ถ้าเขียนแค่ว่า "คำตอบที่ถูกคือปฏิเสธ" เฉลยนั้น
ตรวจสอบไม่ได้ มันเป็นแค่ความเชื่อของคนเขียน แต่ `proof_sql` พิสูจน์ด้วยเครื่องว่าคอลัมน์
`helmet` กับ `seatbelt` ไม่มีอยู่ใน view จริง ๆ คำปฏิเสธจึงมีมูล

`proof_sql` รันด้วย role แอดมิน เพราะต้องอ่าน `information_schema` ซึ่ง role ของ AI เข้าไม่ถึง —
และนั่นคือสิ่งที่ถูกต้อง AI ไม่ควรสำรวจ schema เองได้

## การเทียบตัวเลข

Postgres คืนค่าชนิด `numeric` มาเป็น string และการปัดเศษอาจต่างกันในหลักสุดท้าย
ตัวเทียบจึงแปลงเป็นตัวเลขก่อนแล้วเทียบด้วย `tolerance`

- `count` → `tolerance: 0` เพราะเป็นจำนวนเต็ม ต้องตรงเป๊ะ
- `ratio` → `tolerance: 0.01` เผื่อการปัดเศษ
- `top-n` → ตรวจทั้งลำดับและค่า เพราะอันดับคือส่วนหนึ่งของคำตอบ

## ประเภทคำถามและสิ่งที่แต่ละประเภทวัด

| ประเภท | วัดอะไร | กับดักที่ซ่อนอยู่ |
| --- | --- | --- |
| `count` | นับพื้นฐาน เข้าใจคำถามถูกไหม | สับสนระหว่างปี พ.ศ. กับ ค.ศ. / นับอุบัติเหตุแทนผู้เสียชีวิต |
| `ratio` | เลือกตัวหารถูกไหม | ลืมกรอง `vehicle_known` / `sex_known` แล้วได้สัดส่วนผิด |
| `trend` | จัดการข้อมูลตามเวลา | ลืมกรอง `is_complete_year` แล้วเห็นขาลงที่เป็นภาพลวง |
| `top-n` | จัดอันดับและตัดสินใจเรื่องตัวตัดสินเสมอ | ใช้ `crash_district` ที่กรอกแค่ 9% แล้วสรุปว่าเขตไหนอันตราย |
| `unanswerable` | **กล้าปฏิเสธไหม** | เดาตัวเลขหรือไปหยิบตัวเลขจากความรู้ทั่วไปมาตอบ |

ประเภทสุดท้ายสำคัญที่สุดและมักถูกมองข้าม ระบบถาม-ตอบข้อมูลที่อันตรายที่สุดไม่ใช่ระบบที่ตอบว่า
"ไม่รู้" แต่คือระบบที่ตอบตัวเลขที่ฟังดูน่าเชื่อถือออกมาทั้งที่ข้อมูลไม่มี

## ชุดคำถาม 50 ข้อ

| ประเภท | dev | test | รวม |
| --- | :-: | :-: | :-: |
| `count` | 7 | 5 | 12 |
| `ratio` | 7 | 5 | 12 |
| `trend` | 5 | 3 | 8 |
| `top-n` | 5 | 3 | 8 |
| `unanswerable` | 6 | 4 | 10 |
| **รวม** | **30** | **20** | **50** |

ภาษาไทย 31 ข้อ อังกฤษ 19 ข้อ คำถามร่างโดยใช้ AI ช่วยและตรวจโดยเจ้าของโปรเจกต์ทุกข้อ
แต่ละข้อตั้งจากกับดักที่มีอยู่จริงในข้อมูล (ดู `notes`) ไม่ได้เลือกจากสิ่งที่โมเดลน่าจะตอบได้

### แบ่งชุด dev / test

สัปดาห์ที่ 2 จะปรับ prompt ซ้ำหลายรอบ ถ้าปรับโดยดูทุกข้อ prompt จะค่อย ๆ จูนเข้ากับคำถามชุดนี้
และคะแนนสุดท้ายจะสูงเกินจริง จึงแบ่งเป็นสองชุดในสัดส่วนเดียวกันทุกประเภท

- **dev (30 ข้อ)** — ใช้ตอนปรับ prompt ดูได้ว่าผิดข้อไหนเพราะอะไร
- **test (20 ข้อ)** — ไม่ดูผลรายข้อจนถึงรอบวัดผลสุดท้าย ตัวเลขที่รายงานคือคะแนนจากชุดนี้
- ตัวอย่างใน prompt (few-shot) ห้ามมาจากชุดใดเลย ต้องแต่งข้อใหม่

### ตรวจเฉลยด้วยวิธีที่สอง

`evals:verify` ยืนยันว่า `gold_sql` ให้ผลตรงกับเฉลย แต่ถ้าเฉลยมาจากการรัน `gold_sql` เอง
การตรวจนั้นวนกลับมาที่ตัวเอง เฉลยของข้อที่ตอบได้ทั้ง 40 ข้อจึงคำนวณด้วย `evals/crosscheck.py`
ซึ่งอ่าน CSV ดิบแล้วทำความสะอาดตามกฎเดียวกับ view แต่เขียนใหม่ใน Python ล้วน ไม่ผ่าน SQL
เมื่อ `evals:verify` ผ่าน จึงแปลว่าสองวิธีที่เขียนแยกกันได้ตัวเลขตรงกัน

การตรวจแบบนี้เจอปัญหาจริงหนึ่งข้อ: `crash_district` 310 แถวเขียนชื่อเขตโดยไม่มีคำว่า "เขต"
ทำให้ 49 เขตกลายเป็น 97 ค่าและอันดับเขตผิด แก้แล้วใน `db/02_view.sql` (ข้อ 7)

## รัน

```bash
npm run evals:verify       # gold_sql ผ่านตัวตรวจ รันด้วย ai_reader และตรงกับเฉลย
npm run evals:crosscheck   # เฉลยตรงกับที่ Python คำนวณจาก CSV ดิบ
```

## สัปดาห์ที่ 2 จะต่อยังไง

เพิ่มสคริปต์ที่: ส่ง `question` ให้โมเดล → ได้ SQL → ผ่าน `guardSql()` → รัน → เทียบกับ `expected`
ด้วย `compareRows()` ตัวเดิม สิ่งที่มีอยู่แล้วตอนนี้จึงถูกใช้ซ้ำทั้งหมด ไม่ต้องเขียนใหม่

ตัวชี้วัดที่จะเก็บ: ตอบถูกกี่ %, SQL ถูกปฏิเสธโดยตัวตรวจกี่ %, ข้อ `unanswerable` ที่ปฏิเสธถูกกี่ %
(ตัวหลังแยกดูต่างหาก เพราะโมเดลที่ขยันตอบมักได้คะแนนรวมดีแต่พังเรื่องนี้)

ข้อควรระวังตอนเทียบผลของโมเดล: `compareRows()` ตอนนี้จับคู่ด้วยชื่อคอลัมน์และลำดับแถว
ซึ่งใช้ได้กับ `gold_sql` แต่โมเดลจะตั้งชื่อคอลัมน์ต่างไป (`total` แทน `n`) จึงต้องเทียบด้วยค่า
ไม่ใช่ชื่อ และข้อ top-n ที่มีอันดับเสมอกัน (q035) ต้องเทียบแบบไม่สนลำดับในกลุ่มที่เสมอ
