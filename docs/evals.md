# ชุดทดสอบ (eval harness)

## ทำไมต้องมี

สัปดาห์ที่ 2 จะต่อโมเดลเข้ามาเขียน SQL คำถามที่ตามมาทันทีคือ **"แล้วรู้ได้ยังไงว่ามันตอบถูก"**
ถ้าวัดด้วยการลองถามเองสิบคำถามแล้วรู้สึกว่าดี จะไม่มีทางรู้เลยว่าการแก้ prompt ครั้งต่อไป
ทำให้ดีขึ้นหรือแย่ลง

ชุดทดสอบนี้คือคำถามพร้อมเฉลยที่ตรวจได้ด้วยเครื่อง ใช้เป็นตัวเลขอ้างอิงว่าเปลี่ยนอะไรแล้ว
คะแนนขยับไปทางไหน

## หลักที่ยึด: เฉลยต้องถูกตรวจก่อน

ปัญหาที่เจอบ่อยในชุดทดสอบคือ **เฉลยเองผิด** ซึ่งทำให้ตัวเลขที่วัดได้ไร้ความหมาย
โมเดลอาจตอบถูกแต่ถูกนับว่าผิด หรือแย่กว่านั้นคือตอบผิดแล้วถูกนับว่าถูก

`npm run evals:verify` จึงรัน `gold_sql` ของทุกข้อกับฐานข้อมูลจริง แล้วเทียบกับเฉลยที่เขียนไว้
**สคริปต์นี้ยังไม่ยุ่งกับ AI เลย** มันตอบคำถามเดียวคือ "เฉลยที่เราเขียน ตรงกับที่ฐานข้อมูลตอบจริงไหม"

สคริปต์ยังส่ง `gold_sql` ทุกข้อผ่านตัวตรวจ SQL ด้วย ถ้าเฉลยของเราเองยังเขียน SQL ที่ตัวตรวจ
ไม่ยอมให้ผ่าน แปลว่าเราตั้งกฎไว้แคบเกินไปจนโมเดลก็จะเขียนให้ผ่านไม่ได้เหมือนกัน
และ `gold_sql` ถูกรันด้วย role `ai_reader` ตัวเดียวกับที่ SQL ของ AI จะถูกรัน ไม่ใช่ role แอดมิน

## รูปแบบไฟล์

`evals/questions.jsonl` — หนึ่งคำถามต่อหนึ่งบรรทัด (JSON Lines)

เลือก JSONL แทน JSON ก้อนเดียวเพราะ: diff ใน git อ่านง่ายเวลาเพิ่มทีละข้อ, ไฟล์พังหนึ่งบรรทัด
ไม่ทำให้ทั้งไฟล์ใช้ไม่ได้และบอกได้ว่าพังบรรทัดไหน, และสัปดาห์ที่ 2 อ่านทีละบรรทัดแบบ stream ได้

| ฟิลด์ | ความหมาย |
| --- | --- |
| `id` | รหัสไม่ซ้ำ เช่น `q001` |
| `split` | `dev` หรือ `test` — ดูหัวข้อ "แบ่งชุด dev / test" |
| `question` | คำถามอย่างที่ผู้ใช้จะพิมพ์จริง |
| `lang` | `th` หรือ `en` |
| `type` | `count` · `ratio` · `trend` · `top-n` · `unanswerable` |
| `gold_sql` | SQL ที่ถูกต้อง เป็น `null` เมื่อเป็นคำถามที่ตอบไม่ได้ |
| `expected` | เฉลย — `{kind:"rows", rows:[...]}` หรือ `{kind:"refusal", ...}` |
| `tolerance` | ความคลาดเคลื่อนที่ยอมรับได้ของตัวเลข ใช้กับทศนิยม |
| `notes` | เหตุผลของเฉลย กับดักของข้อนี้ และสิ่งที่คำตอบที่ดีควรพูดถึง |

### ตัวอย่างข้อที่ตอบได้

```json
{"id":"q001","question":"ปี พ.ศ. 2567 มีผู้เสียชีวิต...กี่ราย","lang":"th","type":"count",
 "gold_sql":"SELECT count(*) AS n FROM deaths WHERE year_be = 2567",
 "expected":{"kind":"rows","rows":[{"n":675}]},"tolerance":0,"notes":"..."}
```

### ตัวอย่างข้อที่ตอบไม่ได้

```json
{"id":"q003","question":"ผู้เสียชีวิตใส่หมวกกันน็อกกี่เปอร์เซ็นต์","type":"unanswerable",
 "gold_sql":null,
 "expected":{"kind":"refusal","must_mention":["หมวกกันน็อก","ไม่มีข้อมูล"],
   "proof_sql":"SELECT count(*) AS n FROM information_schema.columns WHERE ...",
   "proof_rows":[{"n":0}]},"notes":"..."}
```

**`proof_sql` คือหัวใจของข้อประเภทนี้** ถ้าเขียนแค่ว่า "คำตอบที่ถูกคือปฏิเสธ" เฉลยนั้น
ตรวจสอบไม่ได้ มันเป็นแค่ความเชื่อของคนเขียน แต่ `proof_sql` พิสูจน์ด้วยเครื่องว่าคอลัมน์
`helmet` กับ `seatbelt` ไม่มีอยู่ใน view จริง ๆ คำปฏิเสธจึงมีมูล

`proof_sql` รันด้วย role แอดมิน เพราะต้องอ่าน `information_schema` ซึ่ง role ของ AI เข้าไม่ถึง —
และนั่นคือสิ่งที่ถูกต้อง AI ไม่ควรสำรวจ schema เองได้

## การเทียบตัวเลข

Postgres คืนค่าชนิด `numeric` มาเป็น string และการปัดเศษอาจต่างกันในหลักสุดท้าย
ตัวเทียบจึงแปลงเป็นตัวเลขก่อนแล้วเทียบด้วย `tolerance`

- `count` → `tolerance: 0` เพราะเป็นจำนวนเต็ม ต้องตรงเป๊ะ
- `ratio` → `tolerance: 0.01` เผื่อการปัดเศษ
- `top-n` → ตรวจทั้งลำดับและค่า เพราะอันดับคือส่วนหนึ่งของคำตอบ

## ประเภทคำถามและสิ่งที่แต่ละประเภทวัด

| ประเภท | วัดอะไร | กับดักที่ซ่อนอยู่ |
| --- | --- | --- |
| `count` | นับพื้นฐาน เข้าใจคำถามถูกไหม | สับสนระหว่างปี พ.ศ. กับ ค.ศ. / นับอุบัติเหตุแทนผู้เสียชีวิต |
| `ratio` | เลือกตัวหารถูกไหม | ลืมกรอง `vehicle_known` / `sex_known` แล้วได้สัดส่วนผิด |
| `trend` | จัดการข้อมูลตามเวลา | ลืมกรอง `is_complete_year` แล้วเห็นขาลงที่เป็นภาพลวง |
| `top-n` | จัดอันดับและตัดสินใจเรื่องตัวตัดสินเสมอ | ใช้ `crash_district` ที่กรอกแค่ 9% แล้วสรุปว่าเขตไหนอันตราย |
| `unanswerable` | **กล้าปฏิเสธไหม** | เดาตัวเลขหรือไปหยิบตัวเลขจากความรู้ทั่วไปมาตอบ |

ประเภทสุดท้ายสำคัญที่สุดและมักถูกมองข้าม ระบบถาม-ตอบข้อมูลที่อันตรายที่สุดไม่ใช่ระบบที่ตอบว่า
"ไม่รู้" แต่คือระบบที่ตอบตัวเลขที่ฟังดูน่าเชื่อถือออกมาทั้งที่ข้อมูลไม่มี

## ชุดคำถาม 50 ข้อ

| ประเภท | dev | test | รวม |
| --- | :-: | :-: | :-: |
| `count` | 7 | 5 | 12 |
| `ratio` | 7 | 5 | 12 |
| `trend` | 5 | 3 | 8 |
| `top-n` | 5 | 3 | 8 |
| `unanswerable` | 6 | 4 | 10 |
| **รวม** | **30** | **20** | **50** |

ภาษาไทย 31 ข้อ อังกฤษ 19 ข้อ คำถามร่างโดยใช้ AI ช่วยและตรวจโดยเจ้าของโปรเจกต์ทุกข้อ
แต่ละข้อตั้งจากกับดักที่มีอยู่จริงในข้อมูล (ดู `notes`) ไม่ได้เลือกจากสิ่งที่โมเดลน่าจะตอบได้

### แบ่งชุด dev / test

สัปดาห์ที่ 2 จะปรับ prompt ซ้ำหลายรอบ ถ้าปรับโดยดูทุกข้อ prompt จะค่อย ๆ จูนเข้ากับคำถามชุดนี้
และคะแนนสุดท้ายจะสูงเกินจริง จึงแบ่งเป็นสองชุดในสัดส่วนเดียวกันทุกประเภท

- **dev (30 ข้อ)** — ใช้ตอนปรับ prompt ดูได้ว่าผิดข้อไหนเพราะอะไร
- **test (20 ข้อ)** — ไม่ดูผลรายข้อจนถึงรอบวัดผลสุดท้าย ตัวเลขที่รายงานคือคะแนนจากชุดนี้
- ตัวอย่างใน prompt (few-shot) ห้ามมาจากชุดใดเลย ต้องแต่งข้อใหม่

### ตรวจเฉลยด้วยวิธีที่สอง

`evals:verify` ยืนยันว่า `gold_sql` ให้ผลตรงกับเฉลย แต่ถ้าเฉลยมาจากการรัน `gold_sql` เอง
การตรวจนั้นวนกลับมาที่ตัวเอง เฉลยของข้อที่ตอบได้ทั้ง 40 ข้อจึงคำนวณด้วย `evals/crosscheck.py`
ซึ่งอ่าน CSV ดิบแล้วทำความสะอาดตามกฎเดียวกับ view แต่เขียนใหม่ใน Python ล้วน ไม่ผ่าน SQL
เมื่อ `evals:verify` ผ่าน จึงแปลว่าสองวิธีที่เขียนแยกกันได้ตัวเลขตรงกัน

การตรวจแบบนี้เจอปัญหาจริงหนึ่งข้อ: `crash_district` 310 แถวเขียนชื่อเขตโดยไม่มีคำว่า "เขต"
ทำให้ 49 เขตกลายเป็น 97 ค่าและอันดับเขตผิด แก้แล้วใน `db/02_view.sql` (ข้อ 7)

## รัน

```bash
npm run evals:verify       # gold_sql ผ่านตัวตรวจ รันด้วย ai_reader และตรงกับเฉลย
npm run evals:crosscheck   # เฉลยตรงกับที่ Python คำนวณจาก CSV ดิบ
```

## การให้คะแนนผลของโมเดล (สัปดาห์ที่ 2)

```bash

npm run evals:run -- --split dev --repeat 3          # สามรอบ รายงานค่าเฉลี่ยและช่วงต่ำสุด–สูงสุด
npm run evals:run -- --split dev --model claude-sonnet-5-5
npm run evals:run -- --split test --repeat 3         # ชุด test: แสดงเฉพาะผลรวม
```

โค้ดอยู่ที่ `src/grading.ts` (ฟังก์ชันล้วน ทดสอบใน `tests/grading.test.ts`) ตัวรันอยู่ที่ `src/scripts/run-evals.ts`

### ข้อที่ตอบได้: เทียบ "ผลจากฐานข้อมูล" ไม่ใช่ "ข้อความที่โมเดลเขียน"

สิ่งที่ถูกตรวจคือ `rows` ซึ่ง `ask()` ได้จากการรัน `final_sql` กับฐานข้อมูลเอง ไม่ใช่ตัวเลขที่โมเดลพิมพ์ใน
คำตอบ เหตุผล: ตัวเลขในข้อความแกะออกมาเทียบได้ไม่แน่นอน ("ราว 92.5%" / "92.52 เปอร์เซ็นต์")
และที่สำคัญกว่าคือ rows คือสิ่งที่หน้าเว็บจะเอาไปวาดกราฟ ถ้า rows ถูก คำตอบที่ผู้ใช้เห็นก็มีฐานที่ถูก

กฎการเทียบ และเหตุผลของแต่ละข้อ

| กฎ | เหตุผล |
| --- | --- |
| **จับคู่ด้วยค่า ไม่ใช่ชื่อคอลัมน์** — หา "การจับคู่คอลัมน์" จากเฉลยไปยังคำตอบ (คอลัมน์ละหนึ่งตัว ไม่ซ้ำ) ที่ทำให้ทุกแถวตรง | โมเดลตั้งชื่อเอง (`total` แทน `n`) ชื่อไม่ใช่ส่วนหนึ่งของคำตอบ |
| **จับคู่ทั้งคอลัมน์ ไม่ใช่หาค่าทีละแถว** | ถ้าดูทีละแถว ค่า 51 ในเฉลยอาจไปตรงกับคอลัมน์อะไรก็ได้ที่บังเอิญเป็น 51 การบังคับให้ทุกแถวใช้คอลัมน์เดียวกันตัดความบังเอิญนี้ |
| **คอลัมน์เกินได้ แต่ขาดไม่ได้** | เฉลยของข้อร้อยละมีทั้ง `pct` และ `n` (ตัวหาร) เพราะคำตอบที่ดีต้องบอกตัวหาร ถ้าคำตอบไม่มีตัวหาร ถือว่าไม่ครบ |
| **จำนวนแถวต้องเท่ากัน** | rows คือตารางคำตอบ ถาม "ปีไหนมากที่สุด" แล้วได้ 14 แถว แปลว่า SQL ไม่ได้ตอบคำถาม แม้แถวแรกจะถูก |
| **ลำดับต้องตรงสำหรับ trend และ top-n** ส่วน count / ratio ไม่สนลำดับ | trend อ่านตามเวลา top-n อ่านตามอันดับ ลำดับคือส่วนหนึ่งของคำตอบ |
| **top-n: แถวที่เสมอกันสลับกันได้ แต่ทั้งกลุ่มต้องอยู่ที่อันดับเดิม** — "เสมอ" คือแถวติดกันที่ต่างกันแค่คอลัมน์เดียว (ป้ายชื่อ) | q035 อันดับ 3–4 เท่ากันที่ 51 ราย ลำดับระหว่างสองเขตขึ้นกับตัวตัดสินเสมอที่คนเขียนเฉลยเลือก (เรียงตามชื่อ) ซึ่งคำถามไม่ได้ขอ |
| **ตัวเลขใช้ `tolerance` ของแต่ละข้อ** | count ต้องตรงเป๊ะ ratio เผื่อการปัดเศษ 0.01 ตามที่เขียนไว้ในเฉลย |
| **ร้อยละตอบเป็นสัดส่วน 0–1 ได้** (เฉพาะคอลัมน์ชื่อ `pct*` ในข้อ ratio/trend) | 92.52 กับ 0.9252 คือค่าเดียวกันคนละหน่วย เทียบหลังคูณ 100 ด้วย tolerance เดิม จึงไม่ได้ผ่อนความแม่นยำ |
| **ปี ค.ศ. ตอบแทนปี พ.ศ. ได้** (คอลัมน์ที่มีคำว่า `year`) | ตรวจกับฐานข้อมูลแล้วว่า `year_be = died_year + 543` ทุกแถวทุกปี คำถามภาษาอังกฤษจึงตอบเป็น 2019 แทน 2562 ได้ ตัวเลขจำนวนต้องตรงเหมือนเดิม |
| **ป้ายชื่อที่ gold_sql ตั้งเองไม่ถูกตรวจ** — ค่าที่ปรากฏเป็น literal หลัง `THEN`/`ELSE` ใน gold_sql | q028 ตั้งชื่อช่วงว่า `'covid'`/`'before'` ซึ่งเป็นชื่อที่คนเขียนเฉลยเลือก เหมือนชื่อคอลัมน์ ส่วนค่าที่มาจากข้อมูลจริง (ชื่อเขต) ไม่มีทางอยู่ในรูปนั้นจึงยังถูกตรวจ |

ข้อจำกัดที่รู้อยู่: ถ้าข้อ top-n มีอันดับเสมอกัน **ที่ขอบ** (เช่นอันดับ 5 กับ 6 เท่ากัน) แถวไหนถูกตัดออกขึ้นกับ
ตัวตัดสินเสมอ ตัวเทียบนี้จัดการกรณีนั้นไม่ได้ ตรวจแล้วว่าข้อ top-n ในชุด dev ไม่มีกรณีนี้ (อันดับ 5/6 ของ q035
คือ 48/39 และอันดับ 3/4 ของ q039 คือ 145/135)

### ข้อที่ตอบไม่ได้: ต้องปฏิเสธ และห้ามแต่งตัวเลข

ผ่านเมื่อครบสองเงื่อนไข

1. `refused.value = true` — ใช้ธงนี้ ไม่ใช่การอ่านข้อความ เพราะหน้าเว็บจะใช้ธงนี้ตัดสินว่าจะวาดกราฟหรือไม่
2. **ไม่มีตัวเลขที่หาที่มาไม่ได้** ในข้อความที่ผู้ใช้เห็น (answer + เหตุผล + caveats)
   ตัวเลขมีที่มาเมื่อตรงกับตัวเลขใน คำถาม · เอกสาร schema ใน prompt · ผล query ที่โมเดลรันระหว่างตอบ
   (หลังปัดให้เท่าความละเอียดที่เขียน เช่น "92.5" ตรงกับ 92.52) ยกเว้นจำนวนเต็ม 0–10 และปีในช่วงข้อมูล

เงื่อนไขที่ 2 กันรูปแบบที่อันตรายที่สุด: ปฏิเสธในธง แต่ข้อความบอกว่า "ไม่มีข้อมูล แต่โดยทั่วไปราว 40%"
ข้อจำกัด: ตัวเลขที่โมเดลคำนวณใหม่จากผล query (เช่นหารสองค่าเอง) จะถูกนับว่าหาที่มาไม่ได้ ซึ่งยอมรับได้
เพราะในคำปฏิเสธ ตัวเลขที่สร้างขึ้นใหม่ควรถูกตั้งคำถามอยู่แล้ว

**`must_mention` ใช้ดูประกอบ ไม่มีผลต่อคะแนน** เพราะเป็นการหาคำแบบตรงตัว คำตอบที่ถูกแต่ใช้คำอื่น
("ไม่มีคอลัมน์นี้" แทน "ไม่มีข้อมูล") จะถูกตัดคะแนนโดยไม่สมควร จึงรายงานแยกเป็น "พบคำครบกี่ %"
ไว้อ่านคู่กัน ถ้าตัวเลขนี้ต่ำมาก ค่อยเปิดดูคำตอบจริงว่าโมเดลอธิบายเหตุผลผิดหรือแค่ใช้คำต่าง

### นับ "ปฏิเสธผิด" แยกไว้

ผลของแต่ละข้อมีชนิดเดียว: `correct` · `wrong_rows` · `false_refusal` · `missed_refusal` ·
`fabricated_number` · `error`

`false_refusal` (ข้อที่ตอบได้แต่โมเดลปฏิเสธ) แยกจาก `wrong_rows` เพราะเป็นปัญหาคนละแบบและแก้คนละทาง
และเป็นตัวเลขคู่ที่ทำให้ "อัตราปฏิเสธถูก" มีความหมาย: ระบบที่ปฏิเสธทุกข้อจะได้ปฏิเสธถูก 100% แต่จะได้
**ปฏิเสธผิด 100% และ accuracy รวมแค่ 20%** (6 จาก 30 ข้อ dev) จึงไม่มีทางได้คะแนนดี
(มี test ยืนยันกรณีนี้ใน `tests/grading.test.ts`)

`error` (API ล้ม, SQL สุดท้ายรันไม่ผ่าน, ตอบไม่ทันในจำนวนรอบ) นับเป็นผิดเสมอ ไม่ตัดออกจากตัวหาร
เพราะผู้ใช้จริงก็เจอ error เหมือนกัน ถ้าตัดทิ้ง ระบบที่ล้มบ่อยจะดูแม่นเกินจริง

### ตัวชี้วัดที่รายงาน

| ตัวชี้วัด | นิยาม |
| --- | --- |
| accuracy รวม / แยกตาม type | ข้อที่ผ่าน ÷ ข้อทั้งหมดในชุด (error นับเป็นไม่ผ่าน) |
| ปฏิเสธในข้อที่ตอบไม่ได้ | ข้อ unanswerable ที่ `refused = true` ÷ ข้อ unanswerable |
| ปฏิเสธถูก | ข้อ unanswerable ที่ผ่านครบสองเงื่อนไข ÷ ข้อ unanswerable |
| ปฏิเสธผิด | ข้อที่ตอบได้ที่ `refused = true` ÷ ข้อที่ตอบได้ |
| ตัวตรวจ SQL ปฏิเสธ | ครั้งที่ `guardSql()` ปฏิเสธ ÷ SQL ทั้งหมดที่ส่งเข้าตรวจ (รวมตอนรัน final_sql ซ้ำ) |
| รอบ tool call เฉลี่ย | จำนวนรอบที่โมเดลเรียก `run_sql` ต่อข้อ (หนึ่งรอบอาจมีหลาย query) |
| token / ค่าใช้จ่าย | รวม input, output, cache write, cache read แล้วคิดราคาตาม `src/pricing.ts` |
| latency | เวลาตั้งแต่เรียก `ask()` จนได้คำตอบ รายงาน p50 และ p95 |

ผลแต่ละรอบบันทึกเป็น JSON ที่ `evals/results/<เวลา>_<model>_<split>.json` (ไม่ถูก commit) และต่อท้าย
หนึ่งบรรทัดใน `evals/results/summary.md` (ถูก commit) บันทึกการปรับปรุงแต่ละรอบอยู่ที่ [evals-log.md](evals-log.md)

### เมื่อ ask() ตอบไม่สำเร็จ (เช่นเครดิต API หมด)

`ask()` ไม่ throw แต่คืน `error` ที่มีชนิด (`src/ask-errors.ts`) พร้อม `answer` เป็นข้อความขออภัยภาษาเดียวกับคำถาม

| ชนิด | ลองใหม่ช่วยไหม | หยุดทั้งชุด eval |
| --- | :-: | :-: |
| `out_of_credit` (เครดิตหมด), `auth` (key ผิด) | ไม่ | ✓ |
| `rate_limited`, `overloaded`, `network` (SDK ลองให้ 4 ครั้งแล้ว) | ช่วย | |
| `model_*`, `final_sql_failed`, `bad_request` | แล้วแต่ชนิด | |

หลักของข้อความที่ผู้ใช้เห็น: **ไม่มีตัวเลข** (ไม่ให้ดูเหมือนคำตอบ), **`refused = false`** (ระบบไม่ได้ตัดสินว่า
ข้อมูลตอบไม่ได้ ถ้าตั้งเป็น true หน้าเว็บจะบอกผิดว่า "ไม่มีข้อมูล"), **ไม่บอกเรื่องภายใน** (เครดิตหมดเป็นเรื่องของ
เจ้าของระบบ ผู้ใช้ทำอะไรไม่ได้ รายละเอียดจริงอยู่ใน `error.detail` สำหรับ log) และ**บอกว่าลองใหม่ช่วยหรือไม่**

ถ้าเครดิตหมดระหว่างคำถาม คำตอบที่โมเดลเขียนไว้ครึ่งทางจะถูกทิ้ง เพราะไม่มีผลจากฐานข้อมูลรองรับ

เครดิตหมดตรวจได้สองแบบ: `402 billing_error` ตามเอกสาร และ `400 invalid_request_error` ที่มีคำว่า
"credit balance" ซึ่งเป็นแบบที่เจอจริงตอนรันครั้งแรก แบบหลังต้องดูข้อความเพราะชนิดซ้ำกับ request ผิดรูปทั่วไป
จึงจำกัดไว้แคบที่สุด ถ้า API เปลี่ยนข้อความ จะตกไปเป็น `bad_request` ซึ่งยังไม่ลองใหม่ — ผิดไปทางปลอดภัย

ตัวรัน eval: เจอ error ที่ทำให้ทุกข้อล้มเหมือนกัน (`fatal`) ครั้งแรก จะหยุดหยิบข้อใหม่ทันที บอกว่าทำไปกี่ข้อ
ใช้เงินไปเท่าไร และ**ไม่บันทึกผล** เพราะผลที่ไม่ครบไม่ได้วัดความสามารถของโมเดล

### กติกาชุด test

`--split test` แสดงและบันทึกเฉพาะผลรวม ไม่มีผลรายข้อทั้งบนจอและในไฟล์ เว้นแต่ใส่ `--reveal`
และใช้ `--only` กับชุด test ไม่ได้ ที่ไม่บันทึกรายข้อลงไฟล์ด้วยเพราะไฟล์ผลลัพธ์คือที่ที่แอบดูได้ง่ายที่สุด
ถ้าเห็นว่าผิดข้อไหนแล้วกลับไปแก้ prompt ชุด test ก็จะกลายเป็นชุด dev อีกชุด และคะแนนที่รายงานจะสูงเกินจริง

## สัปดาห์ที่ 2 จะต่อยังไง (แผนเดิมจากสัปดาห์ที่ 1)

เพิ่มสคริปต์ที่: ส่ง `question` ให้โมเดล → ได้ SQL → ผ่าน `guardSql()` → รัน → เทียบกับ `expected`
ด้วย `compareRows()` ตัวเดิม สิ่งที่มีอยู่แล้วตอนนี้จึงถูกใช้ซ้ำทั้งหมด ไม่ต้องเขียนใหม่

ตัวชี้วัดที่จะเก็บ: ตอบถูกกี่ %, SQL ถูกปฏิเสธโดยตัวตรวจกี่ %, ข้อ `unanswerable` ที่ปฏิเสธถูกกี่ %
(ตัวหลังแยกดูต่างหาก เพราะโมเดลที่ขยันตอบมักได้คะแนนรวมดีแต่พังเรื่องนี้)

ข้อควรระวังตอนเทียบผลของโมเดล: `compareRows()` ตอนนี้จับคู่ด้วยชื่อคอลัมน์และลำดับแถว
ซึ่งใช้ได้กับ `gold_sql` แต่โมเดลจะตั้งชื่อคอลัมน์ต่างไป (`total` แทน `n`) จึงต้องเทียบด้วยค่า
ไม่ใช่ชื่อ และข้อ top-n ที่มีอันดับเสมอกัน (q035) ต้องเทียบแบบไม่สนลำดับในกลุ่มที่เสมอ
