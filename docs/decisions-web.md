ไฟล์นี้เขียนใหม่ในรอบที่สอง (5 พ.ย. 2569) หลังตรวจงานของรอบแรกด้วยตัวเอง รอบแรกเขียนข้อสรุปหลายข้อโดยไม่ได้ตรวจ

## ค. คำนวณ H3 ด้วย `h3-js` ฝั่ง Node ไม่ใช้ extension ของ Postgres

คงไว้ตามรอบแรก เหตุผลที่ยังใช้ได้: ไม่ผูกกับ extension ที่อาจไม่มีบนบริการที่จัดการให้ ใช้ได้ทั้งในเครื่องและตอนย้ายไป Neon โดยไม่เปลี่ยนโค้ด
ตัวคำนวณอยู่ที่ `src/h3-aggregate.ts` (ฟังก์ชันล้วน มี test)

**บั๊กที่เจอรอบนี้:** โค้ดรวมกลุ่มด้วยช่อง res9 แล้วหยิบ res8 ของจุดแรกมาใช้ทั้งกลุ่ม แต่ H3 ไม่ซ้อนกันสนิท ช่อง res9 หนึ่งช่องอาจคร่อมขอบของ res8 สองช่อง
จุดสองจุดในช่อง res9 เดียวกันจึงอาจอยู่คนละช่อง res8 ผู้เสียชีวิตติดขอบจะถูกนับผิดช่อง res8 โดยผลรวมทั้งหมดยังถูก (7,529) จึงตรวจด้วยผลรวมไม่เจอ
พิสูจน์ด้วย test ที่หาช่อง res9 ที่คร่อมขอบจริงแล้วดูว่านับผิด (ล้มก่อนแก้: `expected 2 to be 1`) แก้โดยใส่ res8 ของแต่ละจุดเข้า key การรวม
**ผลกับข้อมูลจริง: ไม่มี** โหลดใหม่แล้วได้ตารางเหมือนเดิมทุกประการ (7,194 แถว, ไม่มีผู้เสียชีวิตรายใดย้ายช่อง) ไม่มีตัวเลขที่เคยรายงานผิด
เป็นบั๊กที่ยังไม่เคยกระทบ ไม่ใช่บั๊กที่กระทบข้อมูล

ตัวตรวจของตัวโหลดเปลี่ยนจาก "ผลรวม = 7529" (ตัวเลขที่จำไว้) เป็น "ผลรวม = จำนวนแถวที่มีพิกัดที่นับสดจาก view" และ `db:check` ตรวจทั้งสองแบบ

## ง. ปีในตาราง API และหน้าเว็บ: ค.ศ. ทั้งระบบ แปลงเป็น พ.ศ. ที่จุดแสดงผลจุดเดียว

ตรวจแล้ว: ตาราง `h3_deaths_monthly.died_year` เป็น **ค.ศ.** (มาจาก `died_year` ของ view) และ `year_be = died_year + 543` ทุกแถวทุกปี
(ตรวจจากฐานข้อมูลจริงทั้ง 16 ปี) ค่าคงที่อยู่ที่ `web/lib/years.ts` ที่เดียว (`DATA_YEAR_MIN = 2011`, `DATA_YEAR_MAX_COMPLETE = 2024`)
และ `db:check` เทียบกับตารางจริงทุกครั้ง

- **API รับ ค.ศ.** ถ้าส่ง พ.ศ. (เช่น 2567) จะได้ 400 พร้อมข้อความ "Buddhist-era years are not accepted" ไม่ใช่ได้ข้อมูลผิดปีเงียบ ๆ
- **หน้าเว็บแสดง พ.ศ.** แปลงด้วย `toBuddhistYear()` จุดเดียว มี test ว่าแปลงกลับได้ทุกปี

## จ. สัญญาของ `/api/h3`

- ต่อช่อง: `{h3_index, count}` หรือ `{h3_index, suppressed: true}` ไม่มีอย่างอื่น (test ตรวจชุดฟิลด์ทั้งหมด)
- **เรียงตาม `h3_index` ไม่ใช่ตามจำนวน** (ตำแหน่งของช่องที่ซ่อนจะบอก 1 หรือ 2 ราย ถ้าเรียงตามจำนวน)
- **400** เมื่อ: `res` ไม่ใช่ 8/9, ปีไม่ใช่ตัวเลข 4 หลัก, ปีนอก 2011–2024, `year_from > year_to`, พารามิเตอร์ซ้ำ, **พารามิเตอร์ที่ไม่รู้จัก**
  และ (ตั้งแต่ 2026-11-06) **query string ที่ไม่ใช่รูปมาตรฐาน** `res=<8|9>&year_from=<yyyy>&year_to=<yyyy>` ครบสามตัว เรียงตามนี้ ไม่เข้ารหัสอักขระ
  ทำให้มี URL ที่ถูกต้องแค่ **210 เส้น** (2 ความละเอียด × 105 ช่วงปี) กันการสร้าง URL ใหม่ไม่จำกัดเพื่อหลบ cache ของ CDN (ดู `docs/deploy.md` หัวข้อ "ปิดช่องหลบ cache")
  ข้อความ 400 ไม่สะท้อนค่าที่ผู้ใช้ส่งมา และ 400 ไม่แตะฐานข้อมูล
  **ตัดค่าเริ่มต้นออกไม่ได้แล้ว:** `/api/h3` เปล่า ๆ และ `?res=8` ได้ 400 (ลูกค้าเดียวคือหน้าเว็บของเรา ซึ่งส่งรูปมาตรฐานเสมอ)
- **503** (ข้อความกลาง ๆ ไม่มีรายละเอียด) เมื่อ: ฐานข้อมูลล้ม, ตารางไม่มี, ไม่มีสิทธิ์/รหัสผ่าน, ข้อมูลในตารางผิดปกติ
  **และเมื่อผลว่างสำหรับช่วงปีที่ถูกต้อง** เพราะช่วงที่ผ่านการตรวจแล้วมีผู้เสียชีวิตทุกปีแน่นอน ผลว่างแปลว่าตารางยังไม่ได้โหลด
  ตอบ 200 แผนที่ว่างจะดูเหมือน "ไม่มีผู้เสียชีวิตเลย" ซึ่งเป็นข้อมูลผิดร้ายแรง (หน้าเว็บก็ไม่วาดแท่งใดเมื่อ API ล้ม และไม่เก็บข้อมูลช่วงปีเก่าไว้ใต้ป้ายช่วงปีใหม่)
- header: 200 cache ได้ (5 นาทีที่เบราว์เซอร์, 1 ชม. ที่ CDN), error `no-store`
- ตรวจที่ `proxy.ts` (ก่อน cache) ไม่ใช่แค่ใน route: route handler เห็นแต่ query ที่ Next เขียนใหม่แล้ว จึงต้องเปิด `skipProxyUrlNormalize` (วัดผลใน docs/deploy.md)
- ลบ `export const dynamic = 'force-dynamic'` เพราะ `cacheComponents` ไม่อนุญาต (build พัง) และไม่จำเป็น route handler เป็น dynamic เองเมื่ออ่าน `request.nextUrl`

## ฉ. ซ่อนช่อง <3 ราย (k = 3)

ตามที่โจทย์กำหนด ใช้กับทุกความละเอียดและทุกช่วงปี ตัวเลข ผลที่วัดได้ และข้อจำกัด (กู้ได้ด้วยการลบหลายคำขอ) อยู่ใน `docs/privacy.md`
บันทึกไว้ตรงนี้เฉพาะการตัดสินใจ: **คง k = 3 ตามโจทย์แม้ที่ res9 จะซ่อน 74% ของช่อง** เพราะ k ที่ต่ำกว่านี้ (2) แทบไม่ให้ประโยชน์ด้านความเป็นส่วนตัว
ส่วนการเพิ่ม k ทำให้แผนที่ว่างยิ่งกว่า ทางที่ควรพิจารณาแทนการเพิ่ม k คือจำกัดตัวกรอง (ช่วงปีตายตัว) หรือเพิ่ม noise
ไม่ทำรอบนี้เพราะเป็นการเปลี่ยนผลิตภัณฑ์ ไม่ใช่การแก้ช่องโหว่ และไม่ได้ขอ

## ช. ความปลอดภัยของการเชื่อมต่อฐานข้อมูลของเว็บ

ตัดสินใจ: **ไม่มีทางสลับ role ในโค้ด ไม่ว่ากรณีใด** รายละเอียดกลไกและ test อยู่ใน `docs/privacy.md` หัวข้อ 4 ที่นี่บันทึกทางเลือกที่ไม่เลือก

- *สลับไป role อื่นเฉพาะตอนพัฒนา (`NODE_ENV=development`)* ไม่เลือก เพราะ dev กับ prod ต่างกันที่ตัวแปรสภาพแวดล้อมตัวเดียว
  และ "ตอน dev ใช้ได้" คือสิ่งที่ทำให้ช่องโหว่หลุดไป prod ได้ง่ายที่สุด
- *ให้ `web_reader` ใช้ชื่ออื่นได้ผ่าน env* ไม่เลือก ชื่อตรึง `web_reader` ทั้ง `WEB_DB_USER` และผู้ใช้ใน `WEB_DATABASE_URL`
- *ตรวจแค่ตอนมีคำขอแรก* ไม่เลือก ตรวจตั้งแต่เริ่มเซิร์ฟเวอร์ (`instrumentation.ts`) ข้ามตอน `next build` เพราะ build ไม่ query
  และ CI ที่ build ก่อน deploy ไม่ควรต้องมีรหัสผ่านฐานข้อมูล

พฤติกรรมที่ทดสอบจริง: `next dev` ไม่มีรหัสผ่าน → ปิดตัว, `next start` ไม่มีรหัสผ่าน → ทุกคำขอได้ `500 Internal Server Error` เปล่า ๆ,
เชื่อมต่อฐานข้อมูลที่ไม่มีตาราง → `503` ข้อความกลาง ๆ (รายละเอียดอยู่ใน log ฝั่งเซิร์ฟเวอร์เท่านั้น)

## ซ. แผนที่ฐาน: OpenFreeMap **Liberty** (ไม่ใช่ Positron) และ `maplibre-gl` 5.x

**Style:** ตรวจ style 3 ตัวของ OpenFreeMap ที่ไม่ต้องใช้ token

| style | ชั้น `fill-extrusion` | หมายเหตุ |
| --- | --: | --- |
| positron | 0 | แบนราบ — ใช้ไม่ได้กับโจทย์ตึก 3 มิติ |
| bright | 0 | แบนราบ |
| **liberty** | **1** (`building-3d`, สูงจาก `render_height`, `minzoom` 14) | **เลือก** |

ตรวจต่อว่า "ความสูงจริง" มีจริงไหม โดยดึง vector tile ระดับ 14 มาถอดรหัส 7 จุดในกรุงเทพฯ (สยาม อโศก สีลม สายไหม ลาดกระบัง หนองจอก บางขุนเทียน)

- **ใจกลางเมืองมีความสูงจริง:** สยาม 149 หลัง สีลม 286 หลัง มีเพียง 1–2% ที่เป็นค่าเริ่มต้น 5 ม. ตึกสูงสุดที่เจอ 315 ม.
- **ชานเมืองมีตึกน้อยมาก:** tile สายไหม 2 หลัง, หนองจอก 4, บางขุนเทียน 4, ลาดกระบัง 17 เพราะ OSM ยังบันทึกไม่ครบ
  ซึ่งตรงกับย่านที่มีผู้เสียชีวิตมาก ผลคือแท่งหกเหลี่ยมในชานเมืองจะลอยอยู่เหนือพื้นที่ที่ตึกว่าง นี่เป็นข้อจำกัดของข้อมูล OSM ไม่ใช่ของโค้ด และเขียนไว้ในกล่องข้อจำกัดบนหน้าเว็บ

ทางเลือกที่ไม่เลือก: ใช้ Positron แล้วเพิ่มชั้น `fill-extrusion` เอง (ได้พื้นสว่างกว่า) ไม่เลือกเพราะต้องดูแล style ที่แก้เอง และโจทย์ระบุให้เลือก style อื่นถ้าตัวแรกไม่มีชั้นตึก

**เงื่อนไขการอ้างอิง (จาก tilejson ของ OpenFreeMap):** `OpenFreeMap © OpenMapTiles Data from OpenStreetMap` แสดงสองที่: ตัวควบคุม attribution
ของ MapLibre (อ่านจาก tilejson อัตโนมัติ) และบรรทัดถาวรท้ายแผงข้อมูลที่ไม่ถูกซ่อนตอนพับแผงบนมือถือ พร้อมลิงก์ไป openstreetmap.org/copyright

**`maplibre-gl` ล็อกที่ `^5.24.0`:** รอบแรกติดตั้ง `^6.16.0` แล้วแผนที่ไม่แสดงผลเลย (หน้าเว็บมีแต่แผง) สาเหตุที่พิสูจน์ได้: maplibre-gl 6 แยกคลาส `Camera` ออก

## ฌ. โครงสร้างโปรเจกต์: `web/` เป็นโปรเจกต์อิสระ (แก้แล้ว 2026-11-06)

**สภาพเดิม (รอบแรกถึงรอบที่สาม):** `package.json` ที่รากประกาศ `workspaces: ["web"]` ขณะที่ `web/` มี `package-lock.json` และ `node_modules` ของตัวเอง
และ lockfile ที่รากไม่มีรายการของ `web` เลย การรัน `npm install <แพ็กเกจ>` ใน `web/` ตรง ๆ จึงทำให้ npm รื้อโครงสร้าง
(`--dry-run`: เพิ่ม 183 ลบ 216 แพ็กเกจ) ต้องใช้ `--prefix "$(pwd)" --workspaces=false` เลี่ยง

**ตัดสินใจ: สองโปรเจกต์แยก ไม่ใช่ workspace จริง** เพราะ Vercel จะ build จาก Root Directory = `web` ด้วย lockfile ของ `web/` เอง และไม่มีอะไรใน `web/`
import จาก `src/` (มี test ตรวจใน `tests/deploy-config.test.ts`) ส่วนทางกลับ `src/scripts/*` อ่านค่าคงที่จาก `web/lib/` (ปี, ข้อเท็จจริงของชุดข้อมูล,
รายการคอลัมน์ที่อนุญาต) ซึ่งเป็นทิศทางที่ยอมรับได้: ค่าคงที่ชุดเดียวกันถูกตรวจกับฐานข้อมูลโดย `db:check` และ `neon:check`

**ทำแล้ว:** ลบ `workspaces` จาก `package.json` ที่รากเท่านั้น lockfile ที่รากไม่ต้องแก้ (`npm install --package-lock-only` ไม่เปลี่ยนอะไร เพราะ
lockfile ไม่เคยรู้จัก `web`)

**พบระหว่างพิสูจน์ (ติดตั้งสะอาดจาก lockfile ของ `web/` ในโฟลเดอร์ว่าง):** `npm run typecheck` ใน `web/` **ล้มบน repo ที่เพิ่ง clone** เพราะ `LayoutProps`
เป็นชนิดที่ Next สร้างให้ตอน build/typegen และ `.next/` ยังไม่มี รอบก่อน ๆ ไม่เห็นเพราะมี `.next/` ค้างจาก build ก่อนหน้า แก้โดยให้ script เป็น
`next typegen && tsc --noEmit`

**ตั้งรากของ Next เอง:** เมื่อมี lockfile สองไฟล์ (ที่รากและใน `web/`) Next เดารากโปรเจกต์ไปที่ราก repo แล้วเตือนทุกครั้งที่ build
`next.config.ts` จึงกำหนด `turbopack.root` และ `outputFileTracingRoot` เป็นโฟลเดอร์ `web/` เอง

## ญ. หน้าจอ

- **แผงข้อมูลเดียว** ซ้ายบนจอใหญ่ (กว้าง 24rem) ล่างบนมือถือ (พับได้) แผนที่เต็มจอ แผนที่ชดเชยพื้นที่ที่แผงบัง (`map.setPadding`) ตัวเมืองจึงไม่ซ่อนอยู่หลังแผง
- **บรรทัดสรุปเห็นตลอดแม้พับแผง** ("แสดง N ราย … มีพิกัดเพียง 62% ของทั้งหมด") และเงื่อนไขการอ้างอิง เพราะข้อจำกัดที่สำคัญที่สุดต้องไม่ถูกซ่อนตอนพับ
- **ตัวอธิบายสีอยู่ก่อนกล่องข้อจำกัด** ลองสลับแล้ว (ข้อจำกัดก่อน) แต่ตัวอธิบายสีสั้นและต้องใช้อ่านแผนที่ทันที ส่วนข้อจำกัดข้อสำคัญสุดอยู่ในบรรทัดสรุปแล้ว
- **สีใช้รากที่สองของจำนวน ความสูงใช้จำนวนตรง ๆ** จำนวนต่อช่องเบ้ขวามาก (ส่วนใหญ่ 3–10 ราย มีไม่กี่ช่องเกิน 30) ถ้าสีเป็นเส้นตรง เกือบทุกช่องจะเป็นสีอ่อนเท่ากัน
  ความสูงเป็นเส้นตรงเพราะตาคนเทียบความสูงได้ตรงกว่า ความสูงสูงสุดของ res8 = 2,200 ม., res9 = 500 ม. (ถ้าสูงกว่านี้แท่ง res9 บังตึกที่เป็นเหตุผลที่ซูมเข้ามา)
- **ช่องที่ซ่อนเป็นหกเหลี่ยมสีเทาแบนราบ** ความสูงคือจำนวน และจำนวนจริงถูกซ่อน ถ้าให้ความสูงคงที่จะอ่านเป็นจำนวนได้
- **ตอน API ล้มต้องล้างแผนที่** ไม่เก็บข้อมูลเก่าไว้ ข้อมูลของช่วงปีเก่าที่ติดป้ายช่วงปีใหม่คือข้อมูลผิด และไม่แสดงตัวเลขใด ๆ
- **ใช้ได้บนมือถือ 375px** วัดจริงด้วย Chrome: `scrollWidth` = 375 และไม่มีองค์ประกอบใดเลยขอบทั้งตอนพับและเปิดแผง ปุ่มและช่องเลือกสูง 44px
  (รวมปุ่มซูมของ MapLibre ที่สูง 29px ตามค่าเริ่มต้น ขยายด้วย CSS บนจอสัมผัส)
- **ฟอนต์ Noto Sans Thai** ผ่าน `next/font/google` (ดาวน์โหลดตอน build ให้บริการจากโดเมนเดียวกัน) ตรวจว่าโหลดจริง `document.fonts.check` = true

**บั๊ก CSS ที่เจอ:** CSS ของ maplibre-gl ตั้ง `.maplibregl-map { position: relative }` แบบไม่อยู่ใน `@layer` ซึ่งชนะ utility `absolute` ของ Tailwind v4 (อยู่ใน layer)
ถ้าใส่ `absolute inset-0` ที่ตัว container ตรง ๆ มันกลายเป็น relative สูง 0px แผนที่ไม่ขึ้น (วัดได้ 1280×0) จึงครอบสองชั้น

## ฎ. การทดสอบลำดับ migration (`04` ก่อน `05`)

ไม่ได้รัน `db:reset` กับฐานข้อมูลจริง (ขออนุญาตแล้ว เจ้าของโปรเจกต์เลือกไม่รัน) ทดสอบสถานการณ์เดียวกันบนฐานข้อมูลชั่วคราวแทนใน container `roaddeaths-db` เดิม
ด้วยการตั้ง `POSTGRES_DB` ชั่วคราว (ตรวจก่อนว่าสคริปต์ชี้ไปฐานข้อมูลชั่วคราวจริง ไม่ใช่ฐานข้อมูลจริง) ครอบคลุม 3 สถานการณ์ และ `db:check` ผ่านทุกครั้ง

1. ฐานข้อมูลเปล่า → `db:setup` (04 สร้าง role ก่อนตารางจะมี แล้ว 05 สร้างตารางและให้สิทธิ์)
2. **ตารางมีอยู่แล้วแต่ยังไม่มี role** (สภาพฐานข้อมูลจริงของคุณตอนนี้) แล้วใส่รหัสผ่านและรัน `db:migrate` (04 สร้าง role และให้สิทธิ์เพราะตารางมีแล้ว)
3. รัน `db:migrate` ซ้ำ (สิทธิ์ต้องไม่เพี้ยน)

ผล: ไม่ต้องแก้ไฟล์ SQL เลย ลำดับ 04→05 ถูกต้องเพราะแต่ละไฟล์ตรวจเงื่อนไขของอีกฝั่ง (04 ให้สิทธิ์ถ้าตารางมี, 05 ให้สิทธิ์ถ้า role มี)
สิ่งที่การทดสอบนี้ไม่ครอบคลุม: ขั้นตอนสร้าง Docker volume ใหม่ (`docker compose down -v`) ซึ่งไม่เกี่ยวกับ role หรือสิทธิ์ และลบฐานข้อมูลจริง

- ปีที่มีพิกัดไม่ถึง 50% มีคำเตือนสีเหลือง และบรรทัดสรุปด้านบนแสดง % ของ**ช่วงที่เลือก** แทน 62% ของทั้งชุด

**`/api/years` endpoint ใหม่:** ส่งเฉพาะ `{year, deaths}` ทั้งเมือง ไม่รับพารามิเตอร์ (ถ้ามีจะได้ 400)
ข้อมูลตารางไม่ครบหรือว่างจะได้ 503 ตัวเลขชุดเดียวกันได้จาก `summary.total_deaths` ของ `/api/h3` ทีละปีอยู่แล้ว
endpoint นี้จึงไม่เปิดข้อมูลเพิ่ม แต่ใช้คำขอเดียวแทน 14

**ช่องที่เลือก / Top 10:** จัดอันดับเฉพาะช่องที่แสดงตัวเลข ช่องที่ซ่อนไม่มีอันดับ
ถ้าบอกว่า "อันดับ 900 จาก 1,450" จะรู้ได้ว่าเป็น 1 หรือ 2 ราย
ตอนบินไปช่อง res8 ซูมไปที่ 11.7 ซึ่งต่ำกว่าจุดสลับ 12.5 ไม่อย่างนั้นแผนที่จะเปลี่ยนเป็น res9 และช่องที่เลือกจะหายไป

## งานค้าง / ไม่ได้ทำรอบนี้

- ยังไม่มีตัวกรองรายเดือน (ตารางรายเดือนพร้อมแล้ว) และการกรองรายเดือนจะทำให้ช่องส่วนใหญ่ถูกซ่อนเกือบหมด
- ยังไม่มี rate limit ที่ API
- ยังไม่มี noise / การจำกัดตัวกรองเพื่อปิดช่องกู้ตัวเลขด้วยการลบ (ดู `docs/privacy.md`)
- ยังไม่ได้ deploy (Neon + Vercel เป็นงานสัปดาห์ 4) เมื่อ deploy ต้องตั้ง `WEB_DATABASE_URL` บนแพลตฟอร์ม (ผู้ใช้ใน URL ต้องเป็น `web_reader`)
  และรัน `db:check` ซ้ำเพราะสิทธิ์บนบริการที่จัดการให้อาจต่างจาก Postgres ในเครื่อง
- ยังไม่ได้ตรวจรายการ extension ของ Neon (ข้อ ค)
- เจาะดูรายเขต (ต้องเพิ่มขอบเขตเขตและตารางสรุปรายเขต) และช่องค้นหาสถานที่ (ต้องมี geocoder ที่ใช้ได้ถูกเงื่อนไข) — ดูข้อ ฐ
- ไทม์ไลน์ยังไม่บอกว่าทำไมปี 2554 และ 2567 มีพิกัดน้อย (ต้องดูที่ต้นทาง data.go.th)
- แท่งของไทม์ไลน์บนจอ 375px กว้าง 21.7px (สูง 96px เว้นห่าง 3px) ผ่านเกณฑ์ระยะห่างของ WCAG 2.2 แต่แคบกว่า 24px
