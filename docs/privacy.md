# ความเป็นส่วนตัวของหน้าแผนที่

เอกสารนี้เขียนให้เล่าตอนสัมภาษณ์ได้ ทุกข้อมีตัวเลขหรือคำสั่งที่รันซ้ำพิสูจน์ได้ ส่วน "สิ่งที่ยังกันไม่ได้" อยู่ท้ายเอกสาร
อ่านก่อนเล่า เพราะผู้สัมภาษณ์มักถามตรงจุดนั้น

## เล่าใน 1 นาที

> ข้อมูลต้นทางเป็นข้อมูลเปิดที่มีพิกัดกับวันที่เสียชีวิตรายแถวอยู่แล้ว ผมเลยไม่ได้พยายามปิดความลับ
> แต่พยายามไม่ให้เว็บของผมทำให้การชี้ตัวบุคคลง่ายขึ้น และจำกัดความเสียหายถ้าเว็บถูกเจาะ
> เว็บส่งให้เบราว์เซอร์แค่ "รหัสช่องหกเหลี่ยม กับจำนวน" ไม่ส่งพิกัด วันที่ อายุ หรือเพศของใครเลย
> ฐานข้อมูลของเว็บเป็น role ที่อ่านได้แค่ตารางสรุปตารางเดียว ต่อให้เว็บมีช่องโหว่ ผู้โจมตีก็ไม่ได้ข้อมูลรายคน
> ช่องที่มีน้อยกว่า 3 รายไม่แสดงตัวเลข และผมวัดแล้วว่ากฎนี้ยังถูกอ้อมได้ด้วยการลบผลของหลายคำขอ จึงบอกไว้ตรง ๆ

## ข้อเท็จจริงตั้งต้น: ข้อมูลนี้เปิดอยู่แล้ว

ไฟล์ `data/bangkok-road-deaths.csv` ดึงจาก data.go.th และมีคอลัมน์ `lat`, `lng`, `dead_date`, `age`, `sex`,
`acc_district` ต่อผู้เสียชีวิตแต่ละราย ใครก็ดาวน์โหลดได้

ดังนั้นสิ่งที่งานนี้ป้องกันจึงไม่ใช่ "ความลับรั่ว" แต่คือ 3 อย่างนี้

1. **ไม่ขยายการเข้าถึง** หมุดบนแผนที่ที่ระบุจุดที่คนหนึ่งเสียชีวิต พร้อมวันที่ อายุ เพศ ต่างจากไฟล์ CSV ในพอร์ทัลมาก
   ผู้ชมทั่วไปเปิดมือถือก็เจอ คนที่รู้จักผู้เสียชีวิตอาจจำได้ทันที ข้อมูลที่ "ถูกเผยแพร่ตามกฎหมาย" ไม่ได้แปลว่า
   "เหมาะจะวางเป็นหมุดให้ทุกคนเห็น"
2. **จำกัดความเสียหาย** ถ้าเว็บถูกเจาะ (SQL injection, ตัวแปรสภาพแวดล้อมรั่ว, dependency มีช่องโหว่) ผู้โจมตีควรได้แค่สิ่งที่หน้าเว็บ
   แสดงอยู่แล้ว ไม่ใช่ฐานข้อมูลทั้งก้อนหรือสิทธิ์ผู้ดูแล
3. **ไม่ทำให้การเชื่อมโยง (linkage) ง่ายขึ้น** พิกัดละเอียด + วันที่ + อายุ + เพศ เมื่อจับคู่กับข่าวหรือโซเชียลมีเดีย
   ระบุตัวบุคคลได้เกือบแน่นอน ช่องหกเหลี่ยมรายปีไม่มีคุณสมบัตินั้น

ผมไม่ได้ประเมินด้านกฎหมาย (เช่น PDPA) ถ้าจะเผยแพร่จริงควรให้ผู้รู้ตรวจอีกชั้น

## 1. ทำไมไม่ส่งข้อมูลรายคน

| ส่งออกจาก `/api/h3` | ไม่ส่ง |
| --- | --- |
| `h3_index` (รหัสช่อง) | พิกัดละติจูด/ลองจิจูด |
| `count` หรือ `suppressed: true` | วันที่ (แม้ระดับวัน) |
| `resolution`, `year_from`, `year_to`, `k` | อายุ เพศ พาหนะ เขต สัญชาติ รหัสโรค |
| `summary` (ยอดรวม 4 ตัว) | `id` ของแถว ชื่อ role ข้อความ error ของฐานข้อมูล |

กันที่ **สามชั้นที่ไม่พึ่งกัน**

1. **ตารางไม่มีข้อมูลนั้นตั้งแต่ต้น** `app.h3_deaths_monthly` มี 8 คอลัมน์ (ช่อง res8/res9, ปี, เดือน, ธงปีครบ, จำนวน, จุดกึ่งกลางช่อง)
   ไม่มี id หรือคอลัมน์รายคนเลย `npm run db:check` ตรวจรายชื่อคอลัมน์ ถ้ามีใครเพิ่ม `died_on` หรือ `age` จะล้มทันที
2. **role ของเว็บอ่านได้แค่ตารางนี้** (หัวข้อ 2)
3. **โค้ดสร้าง response จากฟิลด์ที่ระบุชื่อเอง** ไม่ได้ spread แถวจากฐานข้อมูลออกไป ถ้าวันหนึ่งมีคนเพิ่มคอลัมน์ใน SQL
   ฟิลด์นั้นก็ไม่หลุดถึงผู้ใช้ (มี test ยืนยัน `tests/h3-api.test.ts`)

ระดับความละเอียดที่เลือก (res9 กว้าง ~350 ม., ~0.11 ตร.กม.) ก็เป็นส่วนหนึ่งของการปกป้อง: ใหญ่พอที่ไม่ชี้ถึงบ้านหลังเดียว
(res10 ซึ่งตัดแล้วเฉลี่ย 1.4 รายต่อช่อง และ 91% ของช่องมี <3 ราย จึงไม่เปิดให้เลือก)

## 2. ทำไมแยก role `web_reader`

ฐานข้อมูลมี 3 role ที่มีสิทธิ์ต่างกันโดยเจตนา

| role | ใช้ทำอะไร | อ่านได้ | เขียนได้ |
| --- | --- | --- | --- |
| `app_admin` | migrate, โหลดข้อมูล, รัน eval | ทุกอย่าง | ทุกอย่าง |
| `ai_reader` | รัน SQL ที่ AI เขียน (สัปดาห์ 2) | view `deaths` (ผ่านตัวตรวจ SQL) | ไม่ได้ |
| **`web_reader`** | **API ของหน้าแผนที่** | **`h3_deaths_monthly` ตารางเดียว** | **ไม่ได้ทั้งหมด** |

เหตุผลที่ไม่ให้เว็บใช้ `ai_reader` หรือ admin ร่วมกัน: **สิทธิ์ที่ให้เกินจำเป็นคือความเสียหายที่เกิดตอนถูกเจาะ**
เว็บเป็นส่วนที่เปิดสู่อินเทอร์เน็ต มีโค้ดและ dependency มากที่สุด จึงเป็นส่วนที่ควรมีสิทธิ์น้อยที่สุด
ถ้า SQL ใน route ถูกฉีดคำสั่งแปลกปลอม สิ่งที่แย่ที่สุดที่ทำได้ด้วย `web_reader` คืออ่านตารางสรุปที่หน้าเว็บแสดงอยู่แล้ว

**พิสูจน์ด้วยของจริง ไม่ใช่เชื่อเอกสาร** `npm run db:check` ยิงคำสั่งจริงด้วย `web_reader` (ตรวจ 41 ข้อ ณ 2026-11-06) และบังคับว่าต้องผ่าน
ถ้าไม่มี role หรือรหัสผ่าน จะ **ล้ม** ไม่ใช่ข้าม (เวอร์ชันเก่าพิมพ์ว่า "ข้าม" แล้วยังรายงาน "ผ่านทุกข้อ")

- ไล่ตรวจ **ทุกตารางและ view ใน schema `app`** ที่มีอยู่จริง (ไม่ใช่รายชื่อที่จำไว้ ตารางใหม่ในอนาคตถูกตรวจเอง):
  `SELECT` ได้เฉพาะ `h3_deaths_monthly` ส่วน `deaths` และ `deaths_raw` ได้ `permission denied`
- ตรวจจาก catalog ว่าสิทธิ์ทุกชนิด (SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER รวมระดับคอลัมน์) = `SELECT` บนตารางเดียวเท่านั้น
- ลองเขียน/แก้โครงสร้าง 17 แบบ (INSERT, DROP, CREATE, GRANT, สลับ role, `COPY ... TO PROGRAM` ฯลฯ) ถูกปฏิเสธทั้งหมด
- **ปิดชั้น read-only ของเซสชันแล้วลองเขียนอีกครั้ง** (`SET default_transaction_read_only = off`, `BEGIN READ WRITE`) ต้องได้ `permission denied`
  ไม่ใช่ `read-only transaction` เพราะ read-only เป็นแค่ค่าเริ่มต้นที่เซสชันปิดเองได้ ชั้น "สิทธิ์" ต้องยืนอยู่ได้เอง

## 3. ทำไมตัดช่องที่มีน้อยกว่า 3 ราย

ช่องที่มีผู้เสียชีวิต 1 ราย = หมุดจุดเสียชีวิตของคนคนเดียวในรัศมีร้อยเมตร ช่องที่มี 2 ราย ใกล้เคียงกัน (คนหนึ่งในสองรู้ว่าอีกคนคือใคร)
กฎ **k = 3** (`K_MIN` ใน `web/lib/h3-api.ts`) จึงซ่อนตัวเลขของช่องที่ `count < 3` ใช้กับ **ทุกความละเอียดและทุกช่วงปี** เพราะตัดสิน
จากยอดของช่องหลังกรองแล้ว ไม่ใช่ยอดตลอดกาล

ทำไมต้องใช้กับทุกตัวกรอง: res9 เฉลี่ยแค่ 2.1 รายต่อช่อง ถ้าตรวจแค่ยอดรวมทั้งช่วงปี พอผู้ใช้กรองเหลือปีเดียว ช่องส่วนใหญ่จะเหลือ 1 ราย
และถูกแสดงตัวเลขจริง

**ตัวเลขจริงจาก API** (ช่วงเริ่มต้น พ.ศ. 2554–2567 เฉพาะปีที่ข้อมูลครบ รวม 7,337 ราย)

| ความละเอียด | ช่องที่มีผู้เสียชีวิต | ช่องที่ถูกซ่อน | ผู้เสียชีวิตในช่องที่ถูกซ่อน |
| --- | --: | --: | --: |
| res8 | 1,450 | 596 (41.1%) | 795 ราย (10.8%) |
| res9 | 3,527 | 2,614 (74.1%) | 3,366 ราย (45.9%) |
| res8 กรองปีเดียว (พ.ศ. 2563) | 407 | 384 (94.3%) | 458 จาก 545 ราย (84.0%) |
| res9 กรองปีเดียว (พ.ศ. 2563) | 478 | 472 (98.7%) | 521 จาก 545 ราย (95.6%) |

อ่านตัวเลขนี้ตรง ๆ: **ที่ res9 เกือบครึ่งหนึ่งของผู้เสียชีวิตอยู่ในช่องที่ถูกซ่อน และเมื่อกรองเหลือปีเดียว แผนที่แทบไม่เหลืออะไรให้ดู**
นั่นคือราคาของกฎนี้ หน้าเว็บจึงบอกตัวเลขนี้ในกล่องข้อจำกัดทุกครั้ง ไม่ปล่อยให้ผู้ใช้เข้าใจว่าที่เห็นคือทั้งหมด
ช่องที่ถูกซ่อนแสดงเป็นหกเหลี่ยมสีเทาแบนราบ (เพราะความสูงคือจำนวน และจำนวนจริงถูกซ่อน) ไม่ได้หายไปเฉย ๆ ผู้ใช้จึงรู้ว่า "มีบางอย่างอยู่ตรงนั้น"

รายละเอียดการออกแบบที่ซ่อนอยู่

- **เรียงช่องตามรหัสช่อง ไม่ใช่ตามจำนวน** ถ้าเรียงตามจำนวน ตำแหน่งของช่องที่ซ่อนจะบอกว่าเป็น 1 หรือ 2 ราย
- ยอดรวมของช่องที่ซ่อน (`suppressed_deaths`) ส่งให้ แต่ไม่ส่งรายช่อง

## 4. ทำไมเว็บต้องไม่มีสิทธิ์ admin

เหตุการณ์จริงที่เจอตอนตรวจงานรอบก่อน: `web/lib/db.ts` มีฟังก์ชันที่ **สลับไปใช้ role แอดมินเงียบ ๆ เมื่อไม่มีรหัสผ่านของ `web_reader`**
แปลว่าเมื่อไหร่ก็ตามที่ลืมตั้งค่า (หรือ deploy แล้วตัวแปรหาย) เว็บจะรันด้วย superuser โดยไม่มีใครรู้ และทุกการป้องกันในหัวข้อ 2 ไร้ผล
ความสะดวก "ทำงานต่อได้แม้ตั้งค่าไม่ครบ" คือช่องโหว่

สิ่งที่ทำ (ทุกข้อมี test)

| กลไก | อยู่ที่ | พิสูจน์ด้วย |
| --- | --- | --- |
| ไม่มีรหัสผ่าน → **throw** ไม่สลับ role | `web/lib/web-config.ts` | `tests/web-db-config.test.ts` (วางรหัสผ่านแอดมินไว้ใน env ครบแล้วยัง error) |
| ชื่อ role ตรึงเป็น `web_reader` ใส่ role อื่นใน `WEB_DB_USER` หรือ URL ไม่ได้ | เดียวกัน | test เดียวกัน |
| เซิร์ฟเวอร์ **ไม่ขึ้น** ถ้าไม่มีรหัสผ่าน | `web/instrumentation.ts` | รัน `next dev` และ `next start` โดยไม่ใส่รหัสผ่าน: dev ปิดตัว, production ตอบ 500 เปล่า ๆ ทุกคำขอ (ไม่มีรายละเอียดรั่ว) |
| ตรวจซ้ำหลังเชื่อมต่อว่าเป็น `web_reader` จริงและไม่มีสิทธิ์พิเศษ (superuser/createrole/createdb/replication/bypassrls) | `web/lib/db.ts` | test ของ `assertUnprivilegedWebRole` |
| โค้ดใน `web/` **ห้ามมีคำว่า** `POSTGRES_USER`, `POSTGRES_PASSWORD`, `adminPool`, `app_admin`, `DATABASE_URL` (ที่ไม่ใช่ `WEB_`) | `tests/web-db-config.test.ts` | test สแกนทุกไฟล์ใน `web/` |
| ไม่โหลด `.env` ทั้งไฟล์เข้า process.env ของเว็บ อ่านเฉพาะ 6 ตัวแปรที่อนุญาต | `web/lib/local-env.ts` | test ว่ารหัสผ่านแอดมิน/AI/API key ไม่หลุดเข้ามา |

ข้อสุดท้ายสำคัญ: `.env` ของโปรเจกต์รวมรหัสผ่านแอดมิน รหัสผ่าน AI และ API key ไว้ที่เดียว โค้ดรอบก่อนโหลดทั้งไฟล์ ทำให้ทุกอย่างอยู่ในหน่วยความจำของเว็บเซิร์ฟเวอร์
ต่อให้ไม่เคยถูกเรียกใช้ ก็หลุดได้ง่ายขึ้นผ่านหน้า error หรือ log ที่ dump env

สัปดาห์ 3 เว็บจะเรียก `ask()` ซึ่งใช้ `ai_reader` ได้ (อ่านได้แค่ view `deaths` ผ่านตัวตรวจ SQL) แต่ต้องเพิ่มเป็น pool แยกที่ประกาศชัดเจน
ไม่มีทางลัดไปหาแอดมินไม่ว่ากรณีใด

## 5. ฟีเจอร์รอบที่สาม (ไทม์ไลน์ ช่องที่เลือก Top 10 ลิงก์แชร์) ไม่เปิดข้อมูลเพิ่ม

ทุกฟีเจอร์ใหม่ใช้ตัวเลขที่ API ส่งออกอยู่แล้ว ไม่ได้เพิ่มช่องทางใหม่ไปถึงตัวเลขที่ถูกซ่อน
- **`/api/years`** ส่งยอดทั้งเมืองรายปี ปีละหลายร้อยราย ตัวเลขชุดเดียวกันได้จาก `/api/h3` ทีละปีอยู่แล้ว
  ยังผ่านกฎ k เหมือนกัน เพื่อให้ถ้าวันหนึ่งมีคนเพิ่มตัวกรองเขตหรือเดือน ตัวเลขเล็กจะไม่หลุดโดยไม่ได้ตั้งใจ
- **อันดับและ Top 10** คิดเฉพาะช่องที่แสดงตัวเลข ช่องที่ซ่อนไม่มีอันดับ เพราะอันดับจะบอกว่าเป็น 1 หรือ 2 ราย
- **ไม่ทำกราฟรายปีของช่องที่เลือก** ทั้งที่เว็บต้นแบบมี ยอดรายปีของช่องเดียวส่วนใหญ่คือ 1–2 ราย
  การแสดงตัวเลขเหล่านี้คือการเปิดสิ่งที่ซ่อนไว้ตรง ๆ
- **ลิงก์แชร์** เก็บแค่ช่วงปี ตำแหน่งกล้อง ช่องที่เลือก และ 2D/3D ทั้งหมดอยู่ในเบราว์เซอร์ ไม่ถูกส่งไปเก็บที่เซิร์ฟเวอร์
  ค่าจาก URL ถูกตรวจก่อนใช้ทุกค่า (`web/lib/view-state.ts` และ `tests/view-state.test.ts`)
- **ไม่ใส่ analytics หรือ pixel โฆษณา** เว็บต้นแบบใส่ แต่ไม่จำเป็นสำหรับงานนี้ และจะส่งพฤติกรรมของผู้ชมออกไปภายนอก

ปุ่ม "เล่นทีละปี" ทำให้เห็นมุมมองปีเดียว ซึ่งเป็นมุมมองที่ช่องถูกซ่อนมากที่สุด (res8 ซ่อน 84%) ไม่ได้ทำให้ซ่อนน้อยลง
ส่วนการกู้ตัวเลขด้วยการลบผลหลายคำขอ (ข้อ 1 ด้านล่าง) ยังทำได้เท่าเดิม ไม่ง่ายขึ้นและไม่ยากขึ้น

## สิ่งที่ยังกันไม่ได้ (อ่านก่อนเล่า)

1. **กฎ k<3 ถูกอ้อมได้ด้วยการลบผลหลายคำขอ** วัดจริงแล้ว: ขอช่วง [พ.ศ. 2554..Y] สำหรับ Y ทุกปี (14 คำขอ) แล้วลบผลของปีติดกัน
   กู้ได้ว่า "ช่องนี้ปีนั้นมี 1 หรือ 2 ราย" **2,180 รายการช่อง-ปีที่ res8 และ 801 รายการที่ res9** (รันซ้ำได้: `npm run web:measure-suppression` ขณะเปิดเว็บอยู่)
   นี่คือข้อจำกัดของการซ่อนช่องเล็กเมื่อเปิดให้เลือกช่วงปีซ้อนกัน ไม่ใช่บั๊ก กฎนี้จึงเป็น **กฎการแสดงผล** (ไม่ให้ผู้ชมทั่วไปเห็นหมุดคนเดียว)
   ไม่ใช่การรับประกันทางคณิตศาสตร์ต่อผู้โจมตีที่เขียนสคริปต์ ที่ยอมรับได้เพราะสิ่งที่กู้ได้คือ "ช่องหนึ่งมี 1–2 ราย ในปีหนึ่ง" ไม่มีอายุ เพศ หรือวันที่
   และข้อมูลดิบเปิดอยู่แล้ว แต่ควรรู้ตัวว่าการอ้างว่า "ซ่อนทุกช่องที่น้อยกว่า 3" ไม่เป็นจริงสำหรับผู้ที่ตั้งใจ
   ทางเสริมที่ยังไม่ทำ: จำกัดการเลือกช่วงปีเป็นช่วงตายตัวที่ไม่ซ้อนกัน, เพิ่ม noise (differential privacy), จำกัดอัตราการเรียก
2. **ตาราง `h3_deaths_monthly` เก็บรายเดือนและมีช่องละ 1 ราย** การซ่อน <3 เกิดที่ชั้น API ไม่ใช่ที่ฐานข้อมูล ถ้ารหัสผ่าน `web_reader` รั่ว
   ผู้โจมตีอ่านตารางตรง ๆ ได้ (ช่อง + ปี + เดือน + จำนวน แม้ช่องละ 1 ราย) ยังไม่มีพิกัดดิบ ตัวตน หรืออายุ/เพศ แต่ไม่ได้ถูกซ่อนตามกฎ k
3. **ผลรวมของช่องที่ซ่อนถูกส่งให้ (`suppressed_deaths`)** ตามที่กล่องสรุปต้องแสดง ถ้ามีช่องซ่อนช่องเดียว ผู้ใช้จะรู้ว่าช่องนั้นมี 1 หรือ 2 ราย
   (รู้อยู่แล้วว่า <3 จึงเสียแค่ความต่างระหว่าง 1 กับ 2)
4. **ยังไม่มี rate limit** ผู้ใช้ยิง API ได้ไม่จำกัด (ตอนนี้ cache ที่ชั้น CDN ช่วยเรื่องภาระ แต่ไม่ช่วยเรื่องความเป็นส่วนตัว)
5. **`pg_catalog` อ่านได้โดย role ใดก็ได้** (ข้อจำกัดของ Postgres) `web_reader` เห็นรายชื่อตารางได้ แต่ไม่เห็นข้อมูลในตาราง
6. **ไม่ได้ประเมินด้านกฎหมาย** (PDPA และกฎหมายอื่น)
