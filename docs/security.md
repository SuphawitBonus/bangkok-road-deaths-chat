# ความปลอดภัยของการรัน SQL ที่ AI เขียน

## ปัญหาที่ต้องแก้

ระบบนี้ให้โมเดลภาษาเขียน SQL แล้วเอาไปรันกับฐานข้อมูลจริง ซึ่งแปลว่า
**ข้อความที่ผู้ใช้พิมพ์เข้ามา กลายเป็นคำสั่งที่รันบนฐานข้อมูลได้** ต่อให้ไม่มีใครตั้งใจโจมตี
โมเดลก็อาจเขียน SQL ที่ลบข้อมูลหรือดึงข้อมูลที่ไม่ควรเห็นได้เองโดยไม่ตั้งใจ

สมมติฐานที่ยึดคือ **SQL ที่ออกจากโมเดลถือว่าไม่น่าเชื่อถือเสมอ** ไม่ว่า prompt จะเขียนดีแค่ไหน
prompt เป็นการขอความร่วมมือ ไม่ใช่การบังคับ จึงไม่นับเป็นมาตรการความปลอดภัย

## สองชั้นที่ไม่พึ่งพากัน

| | ชั้นที่ 1 — สิทธิ์ในฐานข้อมูล | ชั้นที่ 2 — ตัวตรวจในโค้ด |
| --- | --- | --- |
| อยู่ที่ไหน | `db/03_security.sql` | `src/sql-guard.ts` |
| ใครบังคับใช้ | Postgres | แอปของเรา |
| ทำงานตอนไหน | ตอนรันคำสั่ง | ก่อนเปิด connection |
| บทบาท | **ชั้นหลัก** | ชั้นเสริม |

หลักการคือ **แต่ละชั้นต้องยืนอยู่ได้เองแม้อีกชั้นพังสนิท** ถ้าตัวตรวจในโค้ดมีบั๊กจนปล่อย
`DROP TABLE` ผ่านไป ฐานข้อมูลก็ยังปฏิเสธอยู่ดี และถ้าวันหนึ่งมีคนเผลอให้สิทธิ์ role มากเกินไป
ตัวตรวจในโค้ดก็ยังไม่ยอมส่งคำสั่งนั้นออกไปตั้งแต่แรก

## ชั้นที่ 1 — สิทธิ์ในฐานข้อมูล

SQL จาก AI รันด้วย role `ai_reader` เท่านั้น ซึ่งถูกจำกัดไว้ตั้งแต่ตอนสร้าง role

```sql
ALTER ROLE ai_reader SET default_transaction_read_only = on;
ALTER ROLE ai_reader SET statement_timeout = '5s';
ALTER ROLE ai_reader SET idle_in_transaction_session_timeout = '10s';
ALTER ROLE ai_reader SET search_path = app;
GRANT USAGE ON SCHEMA app TO ai_reader;
GRANT SELECT ON app.deaths TO ai_reader;   -- สิทธิ์เดียวที่ได้
```

**ตั้งที่ role ไม่ใช่ตั้งตอนเปิด connection** — ถ้าตั้งในโค้ด วันหนึ่งที่โค้ดลืมตั้ง
ข้อจำกัดจะหายไปเงียบ ๆ โดยไม่มีอะไรเตือน แต่ถ้าตั้งที่ role ทุก session ของ role นี้
ได้ค่านี้เสมอ ไม่ว่าใครจะเชื่อมต่อเข้ามาด้วยวิธีไหน แม้แต่เปิด `psql` ต่อเองก็ยังติดข้อจำกัดเดิม

**ไม่มีสิทธิ์แตะตารางดิบ** `app.deaths_raw` ไม่เคยถูก `GRANT` ให้ `ai_reader` เลย
แต่ `ai_reader` ยังอ่านข้อมูลผ่าน view `deaths` ได้ เพราะ**view ใน Postgres รันด้วยสิทธิ์ของ
เจ้าของ view ไม่ใช่สิทธิ์ของคนเรียก** (ค่าเริ่มต้นคือ `security_invoker = off`)
เราจึงเปิดเฉพาะข้อมูลที่ทำความสะอาดแล้ว โดยไม่ต้องเปิดตารางจริงให้เลย

### ชั้นนี้กันอะไรได้

ยืนยันด้วยการยิงคำสั่งจริงด้วย `ai_reader` โดยไม่ผ่านตัวตรวจในโค้ด (`npm run db:check`)

| คำสั่ง | ผล | Postgres ตอบว่า |
| --- | --- | --- |
| `SELECT * FROM app.deaths_raw` | ปฏิเสธ | `permission denied for table deaths_raw` |
| `INSERT INTO ...` | ปฏิเสธ | `cannot execute INSERT in a read-only transaction` |
| `UPDATE deaths SET ...` | ปฏิเสธ | `cannot update view "deaths"` |
| `DELETE FROM deaths` | ปฏิเสธ | `cannot delete from view "deaths"` |
| `DROP VIEW app.deaths` | ปฏิเสธ | `cannot execute DROP VIEW in a read-only transaction` |
| `CREATE TABLE evil (x int)` | ปฏิเสธ | `cannot execute CREATE TABLE in a read-only transaction` |
| `ALTER ROLE ai_reader PASSWORD ...` | ปฏิเสธ | `cannot execute ALTER ROLE in a read-only transaction` |
| `SELECT pg_read_file('/etc/passwd')` | ปฏิเสธ | `permission denied for function pg_read_file` |
| `SELECT pg_sleep(8)` | ปฏิเสธ | `permission denied for function pg_sleep` |

### ชั้นนี้กันอะไรไม่ได้

| ช่องที่เหลือ | ทำไมปิดไม่ได้ | ใครรับไป |
| --- | --- | --- |
| อ่าน `pg_catalog` เช่น `pg_tables`, `pg_roles` | Postgres เปิดให้ทุก role อ่านเป็นค่าเริ่มต้น ปิดไม่ได้โดยไม่พังระบบ | ชั้นที่ 2 |
| อ่าน `information_schema` | เหตุผลเดียวกัน | ชั้นที่ 2 |
| query ที่รันได้แต่หนักและกินเวลาเกือบ 5 วินาที | timeout กันได้แค่ไม่ให้ค้างตลอดไป | ชั้นที่ 2 + LIMIT |
| query ที่ถูกต้องทุกอย่างแต่คืนข้อมูลเป็นแสนแถว | เป็น `SELECT` ที่ถูกกฎหมายทุกประการ | ชั้นที่ 2 (บังคับ LIMIT) |
| ตรรกะผิดจนตอบเลขผิด | ไม่ใช่เรื่องสิทธิ์ | ชุดทดสอบ (`docs/evals.md`) |

ข้อที่ต้องเน้น: **การรั่วของ metadata เป็นสิ่งที่ชั้นฐานข้อมูลปิดไม่ได้**
ถ้ามีแค่ชั้นเดียว ผู้ใช้สามารถหลอกให้ AI เขียน `SELECT * FROM pg_roles` เพื่อดูรายชื่อ role
หรือ `pg_stat_activity` เพื่อดู query ของคนอื่นได้ นี่คือเหตุผลหลักที่ต้องมีชั้นที่ 2

## ชั้นที่ 2 — ตัวตรวจในโค้ด

`guardSql()` รับ SQL เข้ามา แล้วคืนอย่างใดอย่างหนึ่ง: **SQL ที่ตรวจแล้วและต้องเอาไปรัน**
หรือ **เหตุผลที่ปฏิเสธ** ผู้เรียกต้องรัน `result.sql` เท่านั้น ห้ามรันข้อความต้นฉบับ

### ทำไมต้องใช้ parser ไม่ใช่ regex

regex อ่าน SQL เป็นข้อความ แต่ Postgres อ่านเป็นไวยากรณ์ ช่องว่างระหว่างสองอย่างนี้คือช่องโหว่
ตัวอย่างที่การตรวจด้วย regex มักพลาด

| SQL | regex ทั่วไปเห็นว่า | ความจริง |
| --- | --- | --- |
| `SELECT ';'` | มีอัฒภาค = หลายคำสั่ง | อัฒภาคอยู่ใน string เป็นคำสั่งเดียว |
| `SELECT 1 /* ; DROP ... */` | มี DROP = อันตราย | อยู่ในคอมเมนต์ ไม่มีผลใด ๆ |
| `WITH d AS (DELETE FROM deaths RETURNING *) SELECT * FROM d` | ขึ้นต้นด้วย WITH...SELECT = ปลอดภัย | **ลบข้อมูลจริง** |
| `SELECT * INTO evil FROM deaths` | เป็น SELECT = ปลอดภัย | **สร้างตารางใหม่** |

ที่นี่ใช้ **libpg-query** ซึ่งคือ parser ตัวจริงของ PostgreSQL ที่คอมไพล์เป็น WebAssembly
เหตุผลที่เลือกตัวนี้แทน `node-sql-parser` หรือ `pgsql-ast-parser` ซึ่งเขียนไวยากรณ์เลียนแบบขึ้นมาใหม่:
**สิ่งที่ตัวตรวจเห็น ตรงกับสิ่งที่เซิร์ฟเวอร์จะเห็นเป๊ะ ๆ** ถ้าใช้ไวยากรณ์คนละชุด จะมีความเสี่ยงว่า
parser อ่านประโยคหนึ่งเป็นแบบหนึ่ง แต่ Postgres อ่านเป็นอีกแบบ ซึ่งเป็นช่องว่างที่อันตรายที่สุด
สำหรับงานด้านความปลอดภัย ข้อแลกเปลี่ยนคือไฟล์ใหญ่กว่าและเป็น WASM แต่คุ้มมากสำหรับงานนี้

### กฎที่ใช้ตรวจ ตามลำดับ

1. **ต้อง parse ผ่าน** ด้วยไวยากรณ์จริงของ Postgres ไม่ผ่าน = ปฏิเสธ
2. **ต้องมีคำสั่งเดียว** นับจำนวนจาก parser จึงไม่โดนหลอกด้วยอัฒภาคในคอมเมนต์หรือใน string
3. **คำสั่งบนสุดต้องเป็น `SELECT`** (ครอบคลุม `WITH ... SELECT` ด้วย เพราะ CTE ติดอยู่กับ `SelectStmt`)
4. **เดินทั้งต้นไม้ ห้ามมีคำสั่งชนิดอื่นแฝงอยู่ที่ชั้นไหนก็ตาม** — ข้อนี้สำคัญที่สุด
   เพราะ `WITH d AS (DELETE ...) SELECT * FROM d` มีชั้นบนสุดเป็น `SelectStmt` จริง ๆ
   การเช็กแค่ชั้นบนสุดจะปล่อยผ่าน
5. **ห้าม `SELECT ... INTO`** เพราะเป็นการสร้างตาราง ทั้งที่ยังเป็น `SelectStmt`
6. **ห้าม `FOR UPDATE` / `FOR SHARE`** เพราะเป็นการล็อกแถว ไม่ใช่การอ่าน
7. **อ้างถึงได้แค่ view `deaths`** (บวกชื่อ CTE ที่นิยามในคำสั่งเดียวกัน) —
   ข้อนี้คือสิ่งที่ชั้นฐานข้อมูลทำแทนไม่ได้ เพราะ `pg_catalog` เปิดให้ทุก role อ่าน
8. **ฟังก์ชันต้องอยู่ใน allowlist**
9. **ต้องมี `LIMIT`** ถ้าไม่มีจะถูกครอบให้

### ทำไม allowlist ไม่ใช่ denylist

denylist ต้องไล่ปิดทีละช่อง และจะพลาดเสมอเมื่อมีฟังก์ชันที่คนเขียนกฎไม่รู้จัก
ส่วน allowlist ผิดพลาดไปในทางปฏิเสธของที่ควรผ่าน ซึ่งเห็นทันทีและแก้ได้ด้วยการเติมชื่อเข้าไป
หลักคือ **ให้ความผิดพลาดตกไปทางปลอดภัย**

รายการที่อนุญาตครอบคลุมฟังก์ชันรวมยอด วันเวลา ข้อความ และ window ที่งานวิเคราะห์ต้องใช้
สิ่งที่จงใจไม่ใส่คือ `generate_series` (สร้างแถวได้ไม่จำกัด), `pg_sleep`, `pg_read_file`,
`dblink`, `set_config`, `version`, `current_setting` และฟังก์ชันระบบทั้งหมด

ข้อควรรู้จากการทดลอง: ไวยากรณ์มาตรฐานอย่าง `EXTRACT(year FROM d)` และ `SUBSTRING(x FROM 1)`
ถูก parser แปลงเป็น `pg_catalog.extract` และ `pg_catalog.substring` โดยอัตโนมัติ
ตัวตรวจจึงต้องยอมให้ `pg_catalog` เป็น schema นำหน้าได้ แล้วไปตรวจที่ชื่อฟังก์ชันจริงแทน
(ถ้าไม่รู้ข้อนี้ จะบล็อก SQL ที่ถูกต้องโดยไม่รู้สาเหตุ)

### การบังคับ LIMIT

ถ้า SQL ไม่มี `LIMIT` ตัวตรวจจะ**ครอบด้วย subquery** ไม่ใช่ต่อข้อความ `LIMIT` ท้ายคำสั่ง

```sql
SELECT * FROM (
  <SQL เดิม>
) AS guarded_result LIMIT 1000
```

เหตุผลที่ไม่ต่อข้อความท้ายคำสั่ง: ถ้าคำสั่งเดิมเป็น `... UNION ALL SELECT ...` หรือมี
`LIMIT`/`OFFSET` อยู่แล้ว การต่อท้ายจะได้ผลผิดหรือไวยากรณ์พัง ส่วนการครอบใช้ได้กับทุกรูปแบบ
และที่สำคัญคือ **SQL ที่ครอบแล้วถูกเอาไป parse ตรวจซ้ำทั้งชุดอีกรอบ** ถ้าการครอบของเราเอง
ทำให้เกิดอะไรแปลก ๆ ก็จะถูกจับได้ ไม่ใช่เชื่อว่าตัวเองทำถูกแน่นอน

ถ้ามี `LIMIT` อยู่แล้วแต่ใหญ่กว่าเพดาน จะถูกครอบเพื่อกดลงมาเช่นกัน

### ชั้นนี้กันอะไรไม่ได้

- **บั๊กในตัวมันเอง** ถ้ามี node ชนิดใหม่ที่ walker ไม่รู้จัก อาจหลุดได้ → ชั้นที่ 1 รับไว้
- **SQL ที่ถูกกฎทุกข้อแต่ตรรกะผิด** เช่นลืมกรอง `vehicle_known` แล้วได้ 44% แทน 92.5%
  → เป็นหน้าที่ของชุดทดสอบ ไม่ใช่ตัวตรวจ
- **เวอร์ชันของ parser ไม่ตรงกับเซิร์ฟเวอร์** ตอนนี้ใช้ parser ของ PostgreSQL 17 กับเซิร์ฟเวอร์ 17
  ถ้าอัปเกรดฝั่งใดฝั่งหนึ่งต้องอัปอีกฝั่งตาม

## ทดสอบ

```bash
npm test          # 74 ข้อ — ทดสอบตัวตรวจในโค้ดล้วน ไม่ต้องมีฐานข้อมูล
npm run db:check  # ยิงคำสั่งจริงด้วย role ของ AI โดยไม่ผ่านตัวตรวจ
```

แยกกันโดยตั้งใจ: `npm test` ทดสอบชั้นที่ 2 เพียว ๆ รันใน CI ได้โดยไม่ต้องยก Postgres
ส่วน `npm run db:check` ทดสอบชั้นที่ 1 เพียว ๆ ด้วยการ**ข้ามชั้นที่ 2 ไปเลย** ซึ่งเป็นวิธีเดียว
ที่จะพิสูจน์ได้ว่าชั้นที่ 1 ยืนอยู่ได้ด้วยตัวเอง ต้องรันซ้ำอีกครั้งหลังย้ายไป Neon เพราะสิทธิ์
บนบริการที่จัดการให้อาจไม่เหมือน Postgres ในเครื่อง

## สิ่งที่ยังไม่ได้ทำ (สัปดาห์ถัดไป)

- จำกัดจำนวนคำถามต่อผู้ใช้ต่อช่วงเวลา (rate limit) — ตอนนี้ยังไม่มีหน้าเว็บจึงยังไม่จำเป็น
- บันทึก SQL ทุกคำสั่งที่รันพร้อมผลลัพธ์ เพื่อย้อนดูว่าโมเดลเขียนอะไรไปบ้าง
- แยก connection pool ของ AI ให้มีจำนวนจำกัด เพื่อไม่ให้คำถามพร้อมกันหลายคนกินทรัพยากรจนหมด
